## 3. 性能审计

### 3.1 线上实测（公网，n=40/c=5，含 ~90ms 网络往返）

| 端点 | p50 | p95 | 吞吐 |
|---|---|---|---|
| /api/health（无鉴权） | 92ms | 473ms | 30.7 req/s |
| SPA 静态页 | 113ms | 495ms | 24.0 req/s |
| /api/dashboard/stats（最重聚合） | 180ms | 895ms | 14.4 req/s |
| /api/intake/orders（中枢列表） | 149ms | 518ms | —（复测 20/20 全 200） |

剔除公网 RTT 后服务器侧处理延迟约为 p50 5-90ms、p95 <800ms，对管理后台与接收接口**完全达标**。

### 3.2 高并发容量评估（引用 test_intake_stress.py 离线压测口径）

- 接收路径 16.4 单/s（8 并发线程，TestClient 含 ~180ms/请求虚高开销，真实 uvicorn 更高）；消费管线 6.6 条/s/worker。
- 当前业务量（日百级单）对容量余量 **10 倍以上**；全链真实瓶颈为茶姬远程接口时延（设计已用异步队列消化）。

### 3.3 架构注意事项（登记，不阻塞）

| 编号 | 级别 | 描述 |
|---|---|---|
| P-1 | P3 | 服务器与其他业务共用（基线 CPU 65%/load 2.4/内存 65%），高峰互相挤占；备份线程 IO 同盘 |
| P-2 | P3 | 单进程架构（SSE 共享事件循环 + 进程内事件总线）：当前规模正确取舍；未来横向扩需先重构 events_bus 为跨进程 |
| P-3 | P3 | SQLite 单写者：高并发写由 WAL+busy_timeout 串行化；当前量级无虞，写入密集场景再评估 |
