# 霸王茶姬多账号管理系统 — 全局操作日志与监控告警说明

> 版本：1.0 ｜ 日期：2026-09-27 ｜ 依据：`server/oplog.py` / `server/log_monitor.py` / `server/routers/logs.py` / `server/log_setup.py`
> 面向：运维排障（第 7 章可直接对照操作）与后续维护者；查询界面走管理端 API（权限 `audit:read`）

---

## 1. 概览与设计

### 1.1 三套留痕机制的分工

系统里同时存在三套「记录发生过什么」的机制，各管一段，互不替代：

| 机制 | 存储位置 | 定位 | 谁在写 |
|---|---|---|---|
| **AuditLog 审计日志** | `data/app.db` | 管理面「谁做了什么」的审计台账（RBAC 视角，只记管理动作），见 `用户操作文档.md` §7.3 | 各管理路由 `log_audit` |
| **领域明细**（CouponUsageLog + PayEventLog） | `data/app.db` | 券与支付会话的**业务领域明细**：每次带券下单成败、每次支付会话事件流，面向券使用记录/支付事件页面 | `routers/orders.py` / `services/pay_session.py` |
| **oplog 全局操作日志**（本档主角） | `data/logs/oplog.db`（独立库） | **全局统一操作日志**：覆盖订单全流程 + HTTP 请求 + 后台线程心跳 + 系统启停，含级别（INFO/WARN/ERROR）、trace_id 链路关联、异常细节；是**排障与监控告警的数据源** | 双进程 + 后台线程统一走 `log_op()` |

一句话区分：审计日志回答「管理员做了什么」、领域明细回答「这笔券/这次支付怎么样了」、oplog 回答「系统每个动作当时发生了什么、出了什么错、整条链路怎么走的」。

### 1.2 双进程与独立日志库

系统跑两个 FastAPI 进程：

| 进程 | 绑定 | 职责 | process 列取值 | 文本日志 |
|---|---|---|---|---|
| 主 API（main-api） | `127.0.0.1:8000` | 管理面 + 后台线程（order-reconcile / menu-refresh / pay-watcher / log-monitor） | `main-api` | `data/logs/server.log` |
| H5 收银台（pay-portal） | `0.0.0.0:8010` | `/pay/*` 公开路由（手机扫码直开），无后台线程 | `pay-portal` | `data/logs/payportal.log` |

（另有 `cli` / `test` 两个预留标识，供脚本与离线测试使用。）

- **oplog 落独立 SQLite 库 `data/logs/oplog.db`**，与业务库 `app.db` 彻底隔离：双进程 + 三个后台线程本就并发写 `app.db`（WAL 缓解），日志高频写入单独落库——日志库损坏/膨胀不影响业务，保留期清理也只动日志库。
- 存储安全参数：WAL + `busy_timeout=5000` + `synchronous=NORMAL`（短事务，进程并发安全）；每条写入独立连接（量级为每秒个位数）。
- **写入永不抛出**：库写入失败时降级为标准 logger 文本输出并累加失败计数，`log_monitor` 据此触发 `oplog_failure` 告警（「日志存储不可靠」）。
- 进程在启动时调 `init_oplog(process=...)` 显式注册 `process` 列取值；未注册时按 `CHAGEE_PROCESS_NAME` 环境变量兜底，最终默认 `main-api`。

### 1.3 文本日志（log_setup.py）

结构化 oplog 之外，每个进程各有一份**文本日志**（root logger，控制台 + 轮转文件双输出）：

- 主 API → `data/logs/server.log`；收银台 → `data/logs/payportal.log`；
- `RotatingFileHandler`：单文件 5MB × 保留 3 个轮转备份，UTF-8；
- 格式：`%(asctime)s %(levelname)s [%(threadName)s] %(name)s: %(message)s` —— 后台线程日志按 `threadName` 即可区分归属；
- 目录可用环境变量 `CHAGEE_LOG_DIR` 重定向（测试隔离用）；
- 每条 oplog 同时**镜像一行**进文本日志（形如 `OP[main-api] feature.order_create actor=admin ...`，ERROR 级附带异常详情），因此文本日志可做全文检索的兜底。

## 2. op_log 字段说明

### 2.1 字段表

表：`op_log`（库 `data/logs/oplog.db`，建表见 `oplog.py`，幂等）。

| 字段 | 类型 | 说明 | 取值示例 |
|---|---|---|---|
| `id` | INTEGER | 自增主键，全局时间序（查询默认按 id 倒序） | `1024` |
| `ts` | TEXT | 本地时间 ISO 字符串（毫秒精度），可直接字典序比较 | `2026-09-27 15:32:01.123` |
| `level` | TEXT | 级别：`INFO` / `WARN` / `ERROR`（见 2.3 语义） | `INFO` |
| `process` | TEXT | 来源进程：`main-api` / `pay-portal` / `cli` / `test` | `main-api` |
| `actor` | TEXT | 操作者：系统登录名，或伪操作者 `system` / `pay-watcher` / `pay-portal` / `order-reconcile` 等（心跳类日志 actor=组件名；HTTP 访问日志为 `-`） | `admin`、`pay-watcher` |
| `action` | TEXT | 操作类型，沿用审计 action 词表并扩展（见 2.2 词表） | `feature.order_create` |
| `target` | TEXT | 操作对象：账号 `备注名#id` / 订单号 / HTTP 路径 | `茶姬A#3`、`CH0927...` |
| `result` | TEXT | 动作结果（见 2.4 常用值） | `success` |
| `params` | TEXT | 关键参数 JSON（**自动脱敏**，超长截断，上限 4000 字符） | `{"order_no":"CH...","pay_amount":"12.00"}` |
| `error` | TEXT | 异常详情：`类型: 消息` + 尾部 3 行调用栈（异常对象自动带栈；上限 1200 字符） | `ChageeApiError: 下单失败…` |
| `trace_id` | TEXT | 链路 ID，同一请求/操作内全部日志相同（后台线程无请求上下文时为空） | `0927153201-a1b2c3d4` |
| `duration_ms` | INTEGER | 动作耗时（毫秒），非必填 | `856` |

索引：`ts` / `action` / `level` / `trace_id` 各一，支撑查询端点的组合过滤。

**脱敏规则**（`redact()`，写 params 时递归执行）：键名命中 `sk` / `session` / `password` / `passwd` / `secret` / `authorization` / `cookie` / `paytoken` / `accesskey` / `sessionkey`（精确）或含 `token` / `password` / `secret` / `authorization` / `cookie`（子串，忽略大小写与下划线/横线）即整值替换为 `***`；字符串超 512 字符截断；嵌套超 6 层、列表超 50 项防御性截断。

| 前缀 | action | 含义 |
|---|---|---|
| **feature.**（管理面用户动作，与审计词表同源） | `feature.order_settle` | F5 试算（购物车加购 → settlePrice → 草稿） |
| | `feature.order_create` | F5 确认下单（createOrder，0 元成单/差额支付分支） |
| | `feature.order_pay` | 取餐页发起支付（生成支付串/选择支付模式） |
| | `feature.order_continue_pay` | 续付（continuePay 重铸支付串，10 分钟窗口内） |
| | `feature.order_cancel` | 取消订单 |
| | `feature.order_switch_full_price` | 券差额单 → 原价单（取消旧单原价重下，管理面入口） |
| | `feature.order_reconcile` | 手动触发单笔订单校准 |
| **coupon.**（券域） | `coupon.rejected` | 券五重验证拒绝（归属/可用性/有效期/门槛/试算在列任一不过） |

| **order.**（后台订单域） | `order.reconcile` | 定时订单校准线程一轮（order-reconcile） |
| | `order.reconcile_inline` | 查询请求内联触发的订单校准 |
| | `order.switch_full_price` | 原价重下执行（引擎层动作） |
| **pay.**（支付会话域） | `pay.session_minted` | 铸造支付会话（差额单生成支付链接） |
| | `pay.session_reminted` | 重铸支付串（会话不变、支付串刷新） |
| | `pay.watcher_paid` | pay-watcher 轮询发现订单已支付（收口） |
| | `pay.watcher_cancelled` | pay-watcher 发现订单已取消（收口） |

| **http.**（请求链路中间件） | `http.request` | 非幂等请求或 4xx/5xx 的访问日志（见第 3 章） |
| **system.**（系统与线程） | `system.startup` | 进程启动 |
| | `system.heartbeat` | 后台线程心跳（每组件默认 60 秒至多一条） |

查询时 `action` 参数按**前缀**匹配（如 `action=order` 命中全部 `order.*`，`action=feature.order` 命中 `feature.order_*`）。

### 2.3 level 语义

| level | 语义 | 典型来源 |
|---|---|---|
| `INFO` | 正常业务动作 | 下单成功、试算、券同步、心跳、非幂等 HTTP 2xx |
| `WARN` | **可恢复异常与业务拒绝**——值得看一眼但系统自愈/属预期拒绝 | 业务规则拒绝（券验证不过、单次一单拦截）、HTTP 4xx、心跳停滞告警（heartbeat_stale 规则本身为 WARN 级） |
| `ERROR` | **失败且需人工关注** | 下单/支付失败、HTTP 5xx、框架未捕获异常、线程死亡、日志库写入失败 |

### 2.4 result 常用值

| result | 含义 |
|---|---|
| `success` | 业务动作成功（默认值） |
| `failed` | 动作失败（error 字段通常非空） |
| `rejected` | 业务规则拒绝（如券五重验证不过、单次一单拦截） |
| `pending` | 已受理、等待终态（如支付发起后等待支付结果） |
| `expired` | 会话/草稿/窗口过期 |
| `ok` | HTTP 请求 2xx/3xx（仅 `http.request` 使用） |
| `http_400` … `http_5xx` | HTTP 响应状态码（仅 `http.request`，如 `http_403`、`http_502`） |
| `exception` | 中间件/框架层未捕获异常 |

## 3. trace_id 链路

### 3.1 生成与传播

- 请求中间件（`install_request_middleware`，主 API 与收银台双入口共用）为**每个请求**生成新 trace_id：格式 `月日时分秒-8位十六进制随机`（如 `0927153201-a1b2c3d4`），写入上下文变量；
- 请求处理期间所有 `log_op()` 调用**自动携带同一 trace_id**（无需逐处传参）；后台线程无请求上下文，trace_id 为空（跨进程动作由 `process` 列区分归属）；
- trace_id 随响应回写 **`X-Trace-Id` 响应头**——前端/调用方报障时直接提供该头即可精确还原当时链路。

### 3.2 记录策略（防轮询刷屏）

- **GET 且 2xx 的查询不落库**（含 H5 收银台秒级 `/status` 轮询）；但 trace_id 照常生成并通过 `X-Trace-Id` 返回；
- 非幂等请求（POST/PUT/DELETE）、**一切 4xx/5xx 必落库**（对应 WARN/ERROR 级）；
- 噪声路径永不落库：`/static/`、`/api/health`、`/docs`、`/openapi`、`/redoc`；
- 中间件/框架层未捕获异常：落一条 ERROR 级 `http.request`（result=`exception`）后原样上抛。

### 3.3 手动下单全链查询示例

一次手动下单出问题时，两步拿到全链视图：

1. **拿 trace_id**：任选其一——
   - 调用时从响应头取 `X-Trace-Id`（最直接）；
   - 或按时间/操作者先粗查定位那条日志：`GET /api/ops/logs?action=feature.order&start=2026-09-27 15:30`，从结果条目里读 `trace_id` 字段；
2. **查全链**：`GET /api/ops/logs/trace/{trace_id}`——返回该链路**全部日志（正序）**，典型形态：

```
http.request          POST /api/ops/accounts/3/orders        → 请求进入
feature.order_settle  试算（草稿、可用券数）                    → 业务开始
coupon.rejected       券验证拒绝（WARN，若有）                 → 可恢复拒绝
feature.order_create  下单（订单号、应付金额、result）
pay.session_minted    差额支付 → 铸造支付会话（若有）
http.request          POST ... 200/4xx/5xx                   → 请求收口（含 duration_ms）
```

## 4. 查询 API（/api/ops/*）

路由文件 `server/routers/logs.py`，前缀 `/api/ops`。**读取类**（日志/trace/告警列表）统一要求 `audit:read` 权限（operator 角色已含）；**管理动作**（告警确认、手动扫描）要求 `user:manage`。数据源是独立日志库 `data/logs/oplog.db`，与业务库无关。认证方式同其他接口：`Authorization: Bearer <JWT>`。

### 4.1 GET /api/ops/logs — 操作日志分页查询

权限：`audit:read`

| 参数 | 类型 | 说明 |
|---|---|---|
| `level` | string | 精确匹配 `INFO`/`WARN`/`ERROR`（枚举校验） |
| `action` | string | **前缀**匹配（如 `order`、`coupon`、`http`、`feature.order`） |
| `actor` | string | 精确匹配操作者（含伪操作者 `system`/`pay-watcher`/`pay-portal`） |
| `target` | string | 精确匹配操作对象 |
| `trace_id` | string | 精确匹配链路 ID |
| `q` | string | 关键词模糊匹配（扫 params/error/target/actor/action 五个字段） |
| `start` / `end` | string | 时间窗，支持 `2026-09-27` 或 `2026-09-27 15:00` 前缀形式 |
| `page` / `page_size` | int | 分页，page_size 上限 100（默认 20） |

响应示例：

```json
{
  "total": 128,
  "stats": {"INFO": 120, "WARN": 6, "ERROR": 2},
  "items": [
    {
      "id": 1024, "ts": "2026-09-27 15:32:01.123", "level": "INFO",
      "process": "main-api", "actor": "admin",
      "action": "feature.order_create", "target": "茶姬A#3",
      "result": "success",
      "params": "{\"order_no\": \"CH0927...\", \"pay_amount\": \"12.00\"}",
      "error": "", "trace_id": "0927153201-a1b2c3d4", "duration_ms": 856
    }
  ]
}
```

（`stats` 为**当前筛选条件**下的级别统计，可直接做列表页的红黄角标。）

### 4.2 GET /api/ops/logs/trace/{trace_id} — 单链路全量视图

权限：`audit:read`。按 trace_id 取该请求/操作从进入到结束的全部日志（**正序**）。无记录返回 404。

```json
{
  "trace_id": "0927153201-a1b2c3d4",
  "items": [ { "...": "同 4.1 items 单条结构" } ]
}
```

### 4.3 GET /api/ops/alerts — 告警列表

权限：`audit:read`。`scope=open`（默认，只看未确认）/ `all`，分页参数同 4.1。

```json
{
  "total": 2, "open": 1,
  "items": [
    {
      "id": 7, "ts": "2026-09-27 15:40:02", "rule": "error_burst", "level": "ERROR",
      "summary": "最近 5 分钟内出现 4 条 ERROR 级操作日志（≥3）",
      "detail": "{\"count\": 4, \"window_seconds\": 300, \"dedupe_key\": \"...\"}",
      "notif_status": "sent", "notif_error": "",
      "acked": 0, "acked_by": "", "acked_at": ""
    }
  ]
}
```

`notif_status`：`sent`（任一渠道送达）/ `skipped`（未配置渠道）/ `failed`（渠道失败，`notif_error` 有原因）/ `pending`（尚未尝试）。

### 4.4 POST /api/ops/alerts/{alert_id}/ack — 确认告警

权限：`user:manage`。确认（处理完毕）一条告警：置 `acked=1` 并记录确认人与时间。告警不存在或已确认返回 404。

```json
{"ok": true, "alert_id": 7, "acked_by": "admin"}
```

### 4.5 POST /api/ops/logs/scan — 手动触发一轮监控扫描

权限：`user:manage`。不等 30 秒周期立即执行一轮四条规则评估（幂等），返回扫描摘要：

```json
{
  "ok": true,
  "scan": {
    "created_alerts": [],
    "pruned": 0,
    "scanned": {
      "errors_in_window": 0,
      "threads": {"order-reconcile": {"expected": true, "alive": true}, "...": "..."},
      "heartbeats": {"pay-watcher": 3.2},
      "oplog_write_failures": 0
    }
  }
}
```

## 5. 监控告警（log_monitor.py）

### 5.1 监控线程

主 API startup 调 `start_log_monitor_thread()` 启动 daemon 线程（**线程名 `log-monitor`**），间隔环境变量 `CHAGEE_LOG_MONITOR_INTERVAL_SECONDS`（默认 30 秒；≤0 不启动，离线测试用）。**只在主 API 进程运行**——8010 收银台进程不启动，避免双进程重复告警。每轮扫描顺带执行保留期清理（见 5.4）。线程轮次异常自身捕获并继续下一轮，不会死掉。

### 5.2 四条规则

| 规则 | 触发条件 | 默认阈值 | 告警级别 |
|---|---|---|---|
| `error_burst` | 统计窗口内 ERROR 级操作日志条数 ≥ 阈值（业务异常洪峰） | 5 分钟（300s）内 ≥ **3** 条 | ERROR |
| `thread_dead` | 预期应存活的后台线程不在本进程线程列表（关键流程中断）。被看护线程：`order-reconcile` / `menu-refresh` / `pay-watcher`；**「预期启动」判定 = 各自间隔环境变量 >0**（置 0 停线程则监控不误报） | — | ERROR |
| `heartbeat_stale` | 组件心跳停滞：距最近一条 `system.heartbeat` 超过阈值（线程活着但循环卡死，如卡死在无超时的外呼上；心跳写入本身限频 60s，阈值给足裕量） | **600 秒**（10 分钟） | WARN |
| `oplog_failure` | oplog 自身写入失败计数 >0（日志存储不可靠——监控自身的基础设施告警，提示检查磁盘/权限） | >0（逐轮清零重计） | ERROR |

**去重（冷却）**：同规则 + 同摘要的**未确认**告警在冷却期（默认 15 分钟 / 900 秒）内不重复创建——避免 error_burst 类洪峰每 30 秒刷一条。确认（ack）后同问题再触发会新建告警。

### 5.3 告警生命周期与通知渠道

生命周期：**open（acked=0）→ 确认 acked=1（记录 acked_by / acked_at）**。确认入口：`POST /api/ops/alerts/{id}/ack`（管理端按钮或 curl）。无论通知渠道是否配置，每条新建告警都会：

1. 落 `op_alert` 表（可在 `/api/ops/alerts` 查询处理）；
2. 控制台 **logger.error 输出**（值守者当场可见，形如 `【告警】[error_burst] …`）；
3. 按配置尝试外发通知，回写 `notif_status` / `notif_error`。

通知渠道配置文件：`data/alert_config.json`（**全部可选、零新增依赖**；未配置时告警仅落库 + 控制台 ERROR，即 notif_status=skipped）。完整示例：

```json
{
  "webhook": {
    "url": "http://192.168.1.10:8080/hook/chagee-alert",
    "secret": "可选：HMAC-SHA256 签名密钥"
  },
  "smtp": {
    "host": "smtp.example.com",
    "port": 465,
    "ssl": true,
    "user": "alert@example.com",
    "password": "邮箱密码或授权码",
    "from": "alert@example.com",
    "to": ["ops@example.com", "backup@example.com"]
  }
}
```

- **webhook**：POST JSON（`{"type": "chagee_op_alert", "rule", "level", "summary", "detail", "ts", "process"}`）；配置了 `secret` 时对整个 body 计算 **HMAC-SHA256 十六进制签名放入 `X-Signature` 请求头**，接收方可验防伪。回调目标多为内网地址，请求**绕过系统代理**直连（与 payment_events 同策略），超时 10 秒。
- **smtp**：`ssl: true` 走 SMTP_SSL（端口默认 465），`false` 走明文 SMTP（端口默认 25）；`from` 缺省用 `user`；`to` 为收件人数组；主题形如 `[茶姬系统告警][ERROR] <摘要前 60 字>`。
- 任一渠道成功即 `sent`；全部失败为 `failed`（`notif_error` 拼接各渠道失败原因）。

### 5.4 保留期清理

每轮扫描顺带删除超期数据：`op_log` 超过 `CHAGEE_OPLOG_RETENTION_DAYS`（默认 30 天）删除；`op_alert` **已确认且超过 90 天**删除（未确认的永不自动清理，避免漏处理）。返回值 `pruned` 为本轮删除的 op_log 条数。

## 6. 环境变量表

| 变量 | 默认 | 作用 |
|---|---|---|
| `CHAGEE_LOG_MONITOR_INTERVAL_SECONDS` | `30` | 日志监控线程扫描间隔（秒）；**≤0 不启动监控**（离线测试用） |
| `CHAGEE_OPLOG_RETENTION_DAYS` | `30` | op_log 保留天数，每轮扫描清理超期记录；≤0 不清理 |
| `CHAGEE_OPLOG_DB` | `data/logs/oplog.db` | 重定向日志库路径（**测试指向 `data/test_*.db`，避免污染生产日志库**，与 `database.DB_PATH` 重定向约定一致） |
| `CHAGEE_LOG_DIR` | `data/logs` | 重定向文本日志目录（server.log / payportal.log；测试隔离用） |
| `CHAGEE_PROCESS_NAME` | `main-api` | `process` 列取值兜底（未调 `init_oplog(process=...)` 显式注册时生效） |
| `CHAGEE_RECONCILE_INTERVAL_SECONDS` | `60` | 订单校准线程（order-reconcile）间隔；**在监控中的角色：>0 表示该线程「预期启动」**，参与 thread_dead / heartbeat_stale 判定；置 0 停线程且监控不误报 |
| `CHAGEE_MENU_REFRESH_INTERVAL_SECONDS` | `86400` | 菜单规格刷新线程（menu-refresh）间隔；监控语义同上 |
| `CHAGEE_PAYWATCH_INTERVAL_SECONDS` | `2` | 支付会话 watcher（pay-watcher）间隔；监控语义同上 |

三个线程间隔变量因此是**双重开关**：`0` = 不启动该线程 + 监控不再看护它（离线测试逐个置 0 即可全静默）；`>0` = 启动并纳入 thread_dead / heartbeat_stale 看护。

## 7. 运维手册

### 7.1 排障路径：手动下单出问题怎么查

按「先定位、再全链、后旁证」三步：

1. **按时间/人/动作定位**：`GET /api/ops/logs?start=2026-09-27 15:30&end=2026-09-27 15:40&actor=admin&action=feature.order`（或直接 `q=订单号` 全字段模糊搜）。优先看 `level=ERROR` 与 `result=failed/rejected` 的条目；`error` 字段自带异常类型 + 尾部 3 行栈，多数问题到此已可判因。
2. **拿 trace_id 看全链**：从定位到的记录读 `trace_id`（或从事发时前端响应头 `X-Trace-Id` 直接获得），调 `GET /api/ops/logs/trace/{trace_id}` 正序看整条链：请求进入 → 试算 → 券验证（`coupon.rejected` 是 WARN 级业务拒绝，属预期拦截）→ 下单 → 支付会话（`pay.session_minted`/`pay.session_reminted`）→ 请求收口（`duration_ms` 可判断慢在哪段）。跨进程动作看 `process` 列：收银台上的续付/原价重下是 `pay.portal_remint` / `pay.portal_switch_full_price`（process=pay-portal）。
3. **结合旁证**：
   - `data/logs/server.log`（或 `payportal.log`）文本日志全文检索——oplog 的镜像行 `OP[main-api] <action> ...` 可与 op_log 互相印证，ERROR 行附完整异常详情；
   - 差额支付相关再看 **PayEventLog 支付事件流**（领域明细，管理端支付事件页面）与会话状态；
   - 券相关再看 **CouponUsageLog 券使用记录**（验证拒绝/下单失败/回滚均有业务明细行）。

### 7.2 告警处理流程

1. 收到 webhook/邮件通知，或在管理端 `GET /api/ops/alerts`（默认 scope=open）看到未确认告警；
2. 按 `rule` 对照 5.2 排查：`error_burst` → 去 `/api/ops/logs?level=ERROR&start=...` 找洪峰源头；`thread_dead` / `heartbeat_stale` → 看 server.log 对应线程名（`[order-reconcile]` 等）最后输出，判断是崩溃还是卡死（卡死多因外呼无超时）；`oplog_failure` → 检查磁盘空间与 `data/logs/` 写权限；
3. 处理完毕后 `POST /api/ops/alerts/{id}/ack` 确认（记录确认人/时间）；**未确认的同摘要告警 15 分钟内不会重复创建，确认后若问题复发会再建新告警**；
4. 等不及 30 秒周期时（如刚重启后想立即验证）：`POST /api/ops/logs/scan` 手动扫一轮并直接看四条规则评估摘要。

### 7.3 日志库保留期与清理

- 保留期由监控线程每轮自动清理：op_log 默认 **30 天**（`CHAGEE_OPLOG_RETENTION_DAYS` 可调），已确认告警 90 天；无需人工维护；
- 日志库是独立 SQLite（`data/logs/oplog.db`，WAL 模式）：**备份业务库 `app.db` 不包含日志**；需要冷备/归档时直接复制 `data/logs/` 目录（建议停写或接受尾部少量缺失）；
- 文本日志自动轮转（5MB × 3），无需 logrotate；
- 日志库体积异常膨胀时先查 `error_burst` 是否长期反复触发、`CHAGEE_OPLOG_RETENTION_DAYS` 是否被置 0（不清理）。

### 7.4 测试隔离约定

离线测试（`test_*_offlines.py`）运行前把日志相关路径全部指向 test 侧，避免污染生产数据：

```bash
export CHAGEE_OPLOG_DB="$PWD/data/test_oplog.db"   # 日志库重定向
export CHAGEE_LOG_DIR="$PWD/data/test_logs"         # 文本日志目录重定向
export CHAGEE_LOG_MONITOR_INTERVAL_SECONDS=0        # 不启动监控线程
```

需要真跑监控逻辑的测试可直接调用 `log_monitor.run_monitor_scan()`（幂等、同步返回摘要），不起后台线程；被看护线程可用各自 INTERVAL 变量置 0 让监控「不预期」，避免误报告警。
