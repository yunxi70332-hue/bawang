# "不走流量" + "验证码不来" 联合诊断报告

> 针对用户反馈：**"霸王茶姬apk不走流量，我发送了手机号请求验证码，都不来"**
> 分析方式：只读。设备端 SP / `/proc` / logcat 采样 + `libapp.so` AOT 反汇编交叉验证。
> 全文不含真实手机号、密钥、token 与完整请求体（手机号已脱敏）。

---

## 0. 结论速览

这两个现象**根因完全不同**，必须分开处理：

| # | 现象 | 根因 | 性质 | 状态 |
|---|---|---|---|---|
| A | APK「不走流量」 | 系统代理 key **残留**：`global_http_proxy_host=127.0.0.1` / `global_http_proxy_port=8080`，而宿主 8080 无监听 → 走代理的请求被拒 | **我方脚本缺陷引入的副作用** | ✅ 已清除并修复脚本 |
| B | 「不走流量」的另一半 | Dart 的 `findProxyFromEnvironment` 读**环境变量**，不读 Android 系统代理 → Dart 业务流量**结构性直连** | 平台机制，非故障 | 已在 `抓包与CA隐匿方案.md` 第 7 节结案 |
| C | 验证码不来 | 应用实际运行在 **test 环境**（`test-gw.chagee.com` / `test-gj-api.bwcj.com`）；测试环境的短信通道不投递真实短信 | **环境固有**，非故障 | 需业务侧决策（见第 5 节） |
| D | 验证码不来（叠加） | 模拟器**无蜂窝射频**，物理上收不到任何真实短信 | 模拟器固有 | 无解，换真机 |

**一句话**：请求发出去了、服务端也回了成功——问题不在客户端，而在**环境**和**载体的物理能力**。

## 1. 证据链

### 1.1 请求确实发出（logcat）

```
I/flutter: 预取号失败，使用验证码登录
I/flutter: 发送验证码的body {scene: login, mobile: 199****0332, sendObj: 199****0332,
                             phoneCode: 86, blockParam: 不验证, sid: <脱敏>, timestamp: <ts>}
I/flutter: 发送验证码 Instance of 'ChageeBaseResponse'
I/flutter: 发送验证码成功====》
I/flutter: 倒计时开始
```

要点：`phoneCode: 86`（请求里带了中国大陆国家码），`scene: login`。

> 附带观察：`blockParam: 不验证` 由**客户端**拼进请求体。这条参数是否影响服务端风控决策，需服务端侧确认——单看客户端无法定论，但"客户端自报跳过验证"本身是一个值得记录的接口设计点。

### 1.2 服务端确实回了 `code == "0"`（AOT 反汇编证明）

`so_analysis/blutter_out/asm/chagee_cn_login_module/page/phone_login/phone_login_bloc.dart`
—— 响应闭包 `[closure] Null <anonymous closure>(dynamic, ChageeBaseResponse)` @ **0x8da3d4**：

```
0x8da450: r1 = response
0x8da454: r0 = r1->field_b            ; 取 code 字段（String）
0x8da464: r16 = "0"
0x8da478: blr  lr                     ; String.==(code, "0")
0x8da47c: tbnz w0, #4, #0x8da540      ; code != "0" → 跳失败分支
──────────────── 成功分支 ────────────────
0x8da4c4: LoginPageCoordinate.path = "/user-client//message/send"
0x8da4e8: SendCodeResultEvent(true)
0x8da514: StartCountDownEvent()
0x8da530: log("发送验证码成功====》")
0x8da53c: b #0x8da5d4                   ; ret
──────────────── 失败分支 @0x8da540 ────────────────
0x8da558: log("发送验证失败: " + code)
0x8da5a4: ChageeToast::toast(...)       ; 弹 toast
0x8da5b8: SendCodeResultEvent(false)
```

**判定**：`发送验证码成功====》` 只存在于 `code == "0"` 分支。日志中**没有** `发送验证失败:` 也没有 toast，说明服务端返回的就是成功。

这是本次诊断最关键的锚点——它把"验证码不来"从**客户端问题**彻底摘出去。

### 1.3 环境 = `test`（三条独立证据）

#### 证据一：环境解析逻辑（`chagee_global_app/init.dart`）

`ChageeInit::initEnv` @ 0x8f9288：

```
innerInitEnv("release")                      ; ① 先按 release 无条件初始化
isDebug = ...                                 ; ② 反射读 BuildConfig.IsDebug
if (!isDebug) return                          ; ③ 非 debug 到此结束
envStr = SpUtil.getString("c_debug_env")      ; ④ 仅 debug 才读这个键
    == "test"    → innerInitEnv("test")
    == "dev"     → innerInitEnv("dev")
    == "uat"     → innerInitEnv("uat")
    == "release" → innerInitEnv("release")
    else         → innerInitEnv("test")        ; ⑤ 兜底也是 test
```

`innerInitEnv` @ 0x8f9528 内部把结果写进 **两个**静态字段：`selectEnv`（0x10f4，`AppEnvConfig`）与 `EncryptUtils.env`（0xfc4，字符串）。

> 注意：`ChageeEnv.selectEnv()` @0x7f2884 那个"硬返回 uat"的函数**不是**真实入口，它只是 `late` 字段的初值兜底。真实入口是上面的 `initEnv`。**上一轮静态报告的"默认 uat"结论据此修正。**

#### 证据二：SP 键名自带环境前缀（决定性）

`chagee_cn_app_user_module/util/encrypt_utils.dart`：

```
setEncryptKeySP() @0x7f2c88 :  SpUtil::putStringEnv("chagee_encrypt_sp_key", value)
_getEncryptKeySP() @0x7f2e98:  SpUtil::getStringEnv("chagee_encrypt_sp_key")
getBaseUrl()       @0x7f2ddc:  读 EncryptUtils.env（0xfc4）分支
```

`putStringEnv` / `getStringEnv` 会自动拼接环境前缀。**设备上实际落盘的键名是**：

```
flutter.test-chagee_encrypt_sp_key
        ^^^^
```

→ `EncryptUtils.env == "test"`。

#### 证据三：`getBaseUrl()` 分支表 + 运行时连接

```
EncryptUtils.env == "dev"  → https://dev-gj-api.bwcj.com
EncryptUtils.env == "test" → https://test-gj-api.bwcj.com      ← 本机命中
EncryptUtils.env == "uat"  → https://uat-gj-api.bwcj.com
否则                        → https://gj-api.bwcj.com
```

同时 `AppEnvConfig` 静态字段被写入全局 base URL（`StoreStaticField(0x1038, selectEnv.field_7)`），`test` 档的值是：

```
AppEnvConfig.test().field_7 = "https://test-gw.chagee.com"
AppEnvConfig.test().field_b = "https://test-h5-sea.chagee.com"
```

运行时核对（强制重启后连续采样 `/proc/net/tcp`，uid=10079）：

```
remote = E100001C:01BB  →  反转字节 = 28.0.0.225:443
```

而 `nslookup test-gw.chagee.com` → `28.0.0.225`，**与运行时实际连接完全一致**。

> 另注：`28.0.0.225` 之外的 DNS 答案（`28.0.1.x`）是宿主沙箱 DNS 代理合成的地址，不可用于判断。用"实际内核连接 + 域名解析对上"这一组合来交叉验证才可靠。

### 1.4 模拟器无蜂窝射频（叠加因素）

```
$ ip -o link show | grep -E 'rmnet|ccmni|pdp|crmni'   → 无输出
$ SIM MCC                                              → 302（虚拟卡）
I/flutter: 预取号结果 {success: false, code:200023 desc:登录超时}
```

一键登录（移动认证）依赖蜂窝数据接口，模拟器天然没有 → 必然降级到短信验证码。而**短信投递的终点是实体手机的射频**，模拟器无论怎么配都收不到。

## 2. 根因拆解

```
用户操作：输入手机号 → 点"发送验证码"
        │
        ├─ 客户端：拼 body（scene/mobile/phoneCode=86/blockParam）→ POST /user-client//message/send
        │                                                              ✅ 已发出
        ├─ 服务端：返回 code = "0"                                      ✅ 受理成功
        │          但服务端在 test 环境 → 短信通道未向真实号码投递
        │
        └─ 用户侧：等待短信……
                   ├─ 若发到实体手机：模拟器看不到（但真机应该能收到）
                   └─ 若 test 环境不投递：永远等不到
```

## 3. 已执行的修复

### 3.1 清除残留代理 key（解决现象 A）

上轮 `revert` 只执行了 `settings delete global http_proxy`，漏掉了
`global_http_proxy_host` / `global_http_proxy_port`，于是 `http_proxy` 显示 `null`
但 App 仍被指向 `127.0.0.1:8080`。宿主当时无监听 → 连接被拒 → 表现为"不走流量"。

已执行并复核：

```
http_proxy                         = null
global_http_proxy_host             = null
global_http_proxy_port             = null
global_http_proxy_exclusion_list   = null
global_proxy_pac_url               = null
```

### 3.2 修复 `scripts/setup_capture_env.ps1`（三处）

| 位置 | 改动 |
|---|---|
| `status` | 原来只看 `http_proxy`，现改为循环输出全部 5 个代理 key，避免漏判 |
| `apply -SetProxy` | 原来只写 `http_proxy`，现同时写 `global_http_proxy_host/port`，并清掉 `exclusion_list`/`pac_url` |
| `revert` | 原来只删 `http_proxy`，现循环删除全部 5 个 key 并回显复核 |

三者都用 `-AsRoot` 走 guest 脚本执行，键名集中在一处，不会再出现"设了 1 个、清 1 个"的错配。

## 4. 为什么"抓包环境是干净的"但"验证码还是不来"

这两件事无关。CA 覆盖层 `NOT_MOUNTED`、代理全 `null`，说明抓包环境已经完全还原；
验证码不来是**业务环境**（test）与**载体能力**（模拟器无射频）的问题。

## 5. 后续可选动作（需你确认后再执行）

### 选项 1：切到 release 环境（改设备 SP，最直接）

因为 `IsDebug == true`，`initEnv` 会读 `c_debug_env`。往 Flutter SP 写一个键即可在下次启动切环境：

```
flutter.c_debug_env = release   →   https://gj-api.bwcj.com + https://gw.chagee.com
```

- 优点：不改 APK，只改运行时配置，可逆（删键即回退）。
- 风险：**这会指向生产环境**。用 debug 签名的包打生产接口，行为与配置属异常组合，
  是否需要这样做由你决定。
- 我不代你执行，等你明确说"切"再动。

### 选项 2：用 test 环境的白名单号码

若 test 环境配置的是"仅白名单号码下发"，用测试号即可。需要向业务侧确认白名单规则。

### 选项 3：换真机 + 正式包

要真实收短信，这是唯一稳妥路径——只有实体射频能接短信。

### 选项 4：抓 Dart 业务流量（与本次问题独立）

系统代理对 Dart 无效已结案，正解是 `mitmproxy --mode wireguard@51820`。

## 6. 方法论备忘（本轮新增）

1. **`late static` 字段的"硬编码初值函数"未必是真实入口。** `ChageeEnv.selectEnv()` 看起来硬返回 uat，
   但真实环境来自 `initEnv` → `innerInitEnv` → 运行时赋值。只读那个函数会得到错误结论。
   今后遇到 `static late` 字段，必须同时找 `StoreStaticField(该 offset)` 的赋值点。
2. **带环境前缀的 SP 键名是最好的"环境探针"。** `SpUtil::putStringEnv` 把环境拼进键名，
   于是设备上落盘的 `test-` 前缀直接暴露了运行时环境——不需要插桩就能读到。
3. **判定域名归属要用"内核连接 + 解析结果"配对。** 单独的 DNS 答案可能被沙箱代理合成（本例 `28.0.1.x`），
   必须与 `/proc/net/tcp` 里真实 ESTABLISHED 的 IP 对上才有说服力。
4. **改系统代理要动 5 个 key，清也要清 5 个。** 只处理 `http_proxy` 会留下幽灵代理。
