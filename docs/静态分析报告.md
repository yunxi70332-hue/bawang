## 七、`IsDebug=true` 的完整链路（本轮重点发现）

这是一条**从 Java 常量一路走到运行环境选择**的完整证据链，也是本包最值得处理的问题。

### 7.1 取值来源

```
Dart 侧
  ChageeEnv::initEnv()                        // chagee_global_app/chagee_env.dart
    → UserAppUtils::isDebug()  @0x8f97f8      // chagee_cn_user_service/user_app_utils.dart
        → ChageeChannelNative::call({"key": "IsDebug"})   // @0x8f98a8，MethodChannel
Java 侧
  MainActivity::getBuildConfigValue("IsDebug")
    → Class.forName("<pkg>.BuildConfig").getField("IsDebug").get(null)   // 反射
    → 返回 BuildConfig.IsDebug = "true"
回 Dart
  与字面量 "true" 比较 → ChageeEnv.isDebug = true（静态字段 offset 0x10fc）
```

注：`getBuildConfigValue` 是**通用反射桥**，按 key 名读取 BuildConfig 任意字段——Dart 侧可以拿到 `BuildConfig` 里的任何常量。

### 7.2 `isDebug=true` 的实际影响（已定位三处）

| 位置 | 影响 |
|---|---|
| `trace_config.dart` @0x7fee78 / @0x7feec8 | 决定**埋点上报项目**：debug 走 `…/sa?project=mys_dev`，否则 `…/sa?project=mys_production`。即本包埋点会进 **mys_dev** |
| `init.dart` @0x550e98 | 配合 `LoggerModule` 控制 **日志输出开关**（`print`） |
| `init.dart` @0x80a4c8（`setNativeH5Domain` @0x80a418） | 结合 `SpUtil.getString("c_debug_env")` 与字面量 `"test"` 决定 **native H5 域名** |

### 7.3 环境矩阵与环境解析

`env_app.dart` 内置四套环境：

| 环境 | API 网关 | H5 |
|---|---|---|
| release | `https://gw.chagee.com` | `https://h5-sea.chagee.com/` |
| uat | `https://uat-gw.chagee.com` | `https://uat-h5-sea.chagee.com/` |
| test | `https://test-gw.chagee.com` | `https://test-h5-sea.chagee.com` |
| dev | `https://dev-gw.chagee.com` | `https://dev-h5-sea.chagee.com` |

`init.dart::envString()` @0x7f2724 的逻辑：

```
if (isDebug) { 按 ChageeEnv.selectEnv 解析 "test" / "dev" / … }   // debug 分支
else        { 走 release 分支 }
```

而静态恢复显示 **`ChageeEnv.selectEnv()` @0x7f2884 直接返回 `AppEnvConfig::uat`**。

**综合判断**：本包 `BUILD_TYPE=release`，但 `IsDebug="true"` 使 Dart 侧进入 debug 分支，环境解析默认落到 **uat**；同时存在本地 SharedPreferences 键 `c_debug_env` 作为覆盖入口。

> ⚠️ **边界**：`envString()` 的最终返回值会受运行时 SP / 远端配置影响，**静态层无法确定设备上真实生效的域名**。上面是"静态可达集合 + 默认分支"的结论，必须用脱敏运行期证据（启动日志中的实际请求 host）坐实。

**因此本包的实际行为是：一个 release 签名的包，以 debug 形态运行，默认指向测试环境。** 建议优先按"打包配置事故"处理。

### 8.2 签名算法（本轮新还原）

`generateSign` 的指令序列可完整串出：

```
取 map 的 keys → ListBase::sort（键名排序）
  → closure: 拼 "键=值"            // 字面量 "="
  → ListIterable::join("&")         // 字面量 "&"
  → Utf8Encoder::convert            // 数据转字节
  → Utf8Encoder::convert            // 密钥转字节
  → Hmac::Hmac + Hmac::convert      // package:crypto
  → base64Encode(digest.bytes)
  → trim()
```

即 **`sign = base64(HMAC(secretKey, "k1=v1&k2=v2&…"))`**，键名参与排序、`&` 连接，结果写入请求头 `sign`。

> **边界**：HMAC 的摘要实现（SHA256/SHA1/…）由构造入参决定，**静态层未能确定**。需运行期观测或与脱敏抓包交叉验证。

### 8.3 请求 / 响应信封

| 方向 | 链路 | 依据（字面量） |
|---|---|---|
| 请求 | `_handleRequestPostBody` → 读 `requestEncryptFields` / `sk` / `signFields` / `secretKey` / `sign` → `AES` / `Encrypted.fromUtf8` → `buildEncryptedDataFromOriginal` → `Encrypter.encrypt` → `Encrypted.base64` | 失败文案 `"请求体加密失败: "`、`"sign failed: "` |
| 响应 | `_decryptResponseIfNeeded` → 读 `responseEncryptFields` / `sk` → `AES` → `decryptFieldsInResponse` → `Encrypter.decrypt64`（Map/List 递归） | 失败文案 `"字段解密失败 ["`、`"] -> "` |
| 补充 | `_handleRequestHeaders` → `NetHeaderService.headers`；`_handleCustomBaseUrl` → 覆盖 `baseUrl` | 字面量 `customHeaders` / `customBaseUrl` |

**这是"字段级"而非"整体"加密**：只有被配置进 `*EncryptFields` 的字段才加/解密，其余字段明文。密钥统一来自服务端 `getsk` 并缓存本地。

## 十、安全态势（静态结论）

| 检测项 | 结果 | 依据 |
|---|---|---|
| 应用级反 Frida / Xposed | ❌ 无 | 关键字命中均为库字符串表误报（`Exposed` 等）；无应用级检测逻辑 |
| 应用级反调试 | ❌ 无 | 无应用级 `isDebuggerConnected` 逻辑 |
| 应用级 Root / 模拟器**阻断** | ❌ 无 | 见下方说明 —— 检测清单存在，但**均属第三方 SDK，且只用于采集/上报** |
| 应用级证书锁定 | ❌ 无 | Dex 层 `CertificatePinner` 全在 okhttp3 库内部，**无 `sha256/<pin>` 常量**；Dart 层无 `badCertificateCallback` / `SecurityContext` |
| 动态 DEX 加载 | ❌ 无 | `DexClassLoader` 命中归于极光 SDK |
| **明文流量** | ⚠️ **允许** | `usesCleartextTraffic=true` |
| **信任用户 CA** | ⚠️ **是** | 清单引用 debug 版 networkSecurityConfig |
| 完整性自校验 | ❌ 无 | 无签名/包名校验逻辑 |

### 关于"Root / 模拟器检测"的准确表述

Dex 中**确实存在**典型的 Root/模拟器检测特征串（`/dev/qemu_pipe`、`/dev/socket/qemud`、`genyd`、`/system/bin/su`、`/system/xbin/su`、`Superuser.apk`、`goldfish`、`google_sdk`、`Genymotion`、`deviceIsEmulator`、`isDeviceRooted`）。但归属核实结果是：

| 归属 | 类 | 用途 |
|---|---|---|
| 极光推送 | `cn/jiguang/bu/b.java`、`cn/jiguang/bz/i.java` | 设备画像采集 |
| 支付宝 SDK | `com/alipay/sdk/m/d0/b.java`、`com/alipay/sdk/m/v/b.java` | 风控环境判定 |
| Sentry | `io/sentry/android/core/internal/util/RootChecker.java` | 崩溃报告附加上下文 |
| 神策 | `deviceIsEmulator` / `setDeviceIsEmulator` | 事件属性 |

**没有一处属于应用自身业务代码，也没有一处用于阻断运行。** 因此结论仍为"应用不做自身防护"，但不宜简单写作"无任何检测"。

**综合判断**：客户端几乎不做自身防护，把安全完全建立在 **Dart 层的业务加签 + 字段级 AES** 上。这套设计对"篡改客户端逻辑"没有抵抗力——只要能改到 `libapp.so`，签名与加密流程本身即可被复现或绕过。真正的验收边界在服务端。

## 十二、结论边界（重要）

1. 本报告全部为**静态推断**。函数地址、字段名、调用关系来自 Blutter 的 AOT 恢复结果，需与原始 `libapp.so` 及脱敏运行期证据交叉验证。
2. **未验证任何服务端验收规则**。客户端存在加签/加密代码路径，不等于服务端接受条件；不得据此推断可绕过服务端校验。
3. HMAC 摘要算法、`sk` 的实际取值与派生方式、`*EncryptFields` 的具体字段清单，**均未在静态层确定**。
4. `envString()` 的运行时最终结果受 SP（`c_debug_env`）与远端配置影响，**静态层无法确定真机实际域名**。
5. 未持有测试账号与已脱敏抓包，登录后状态机与字段字典尚未建立。
6. 所有 ARM64 RVA 仅在 `so_analysis/native/arm64-v8a/libapp.so`（`8b4aa0dd…7da5edd7`）内有效。
7. 本报告不包含任何真实令牌、手机号、Cookie、密钥或完整请求体。
